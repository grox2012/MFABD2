# MFABD2 本地补丁维护指南（给执行版本更新的 agent）

> 你正在更新 MFABD2（换新版本、同步上游、重装发布包）——**先读完本文件再动手**。
> 本机有一组「本地补丁」：对上游 pipeline 资源的定点修复。它们不住在部署目录里，
> 住在本仓库 `patches/` 目录；换版本时部署目录会被整体替换，补丁不会自己跟过去，
> **必须由你按本指南重打并验证**。漏打不一定会立刻报错——它们修的恰恰是
> 「任务假绿勾、实际没效果」的静默失败，漏打 = 故障复活且无人察觉。

## 1. 文件地图

| 文件 | 作用 |
|---|---|
| `patches/manifest.json` | 机器可读清单：每个补丁的 intent、目标文件、编辑锚点、applied 判据、验证方法、退役条件。**唯一事实源** |
| `patches/apply_patches.py` | 幂等重打工具：`--check` 出三态报告，`--apply` 按锚点外科式重打（逐文件备份 + JSON 校验） |
| `patches/PATCH_MAINTENANCE.md` | 本文件：流程与冲突 playbook |
| runbook `references/fix-lifecycle.md` §7 | 本机资源改动清单（与 manifest 应一致，更新时两边都要改） |

当前补丁一览（详情以 manifest 为准）：
- `pass-enter-wait`：Pass.json，通行证进页等待 90 秒，治「15 秒假绿、领取零执行」。
- `quickhunt-locked-stage-fail`：Battle.json，未解锁关卡命中「难度挑战」即显性失败，
  治「米饭不动却报成功」。
- `event-battle-ismenu-roi`：EventBattle.json，赛季挑战关详情页离开判定 roi 扩大（未证成未证伪，观察中）。
- `global-victory-return`：Global.json，复位链加胜利结算出口（2026-10-09 已验证通过）。

## 2. 版本更新标准流程（写死，逐项做）

1. **更新前**：对当前在用的资源目录跑一次
   `python3 patches/apply_patches.py --check --resource-dir <旧版 pipeline 目录>`，
   把输出存进当次更新记录——这是「更新前哪些补丁活着」的证据。再把旧版整个
   `resource` 目录复制一份留底（回滚用）。
2. **装新版**（新目录/覆盖安装都行），确认新版的 pipeline 目录路径。
3. **对新版跑 --check**，按每个补丁的三态处理：
   - `APPLIED`：新版原生已带等效内容。再核对 manifest 该条的 `retire_when`——
     条件满足就把它的 `status` 改成 `retired` 并注明日期与证据（走第 4 节退役流程），
     没满足（如只是碰巧 marker 命中一部分）按 CONFLICT 处理并汇报。
   - `PENDING`：锚点完好。跑 `--apply` 重打，然后**重启 MFAAvalonia**
     （资源在应用启动时缓存，不重启不生效），再进第 5 步抽验。
   - `CONFLICT`：锚点漂移。**禁止硬改、禁止猜着打**，进第 3 节 playbook。
   - `RETIRED`：跳过，什么都不做。
4. **部署侧备份**：`--apply` 会自动在目标文件旁生成 `<文件>.bak-<日期>-<补丁id>`，
   不要删；同一补丁的后续重打不覆盖已有备份。
5. **抽验**：按 manifest 每条的 `verify` 方法，至少对本次新打的补丁各验一次。
   结论只许用三态如实写：**通过 / 复卡（同签名再现，附新证据）/ 未走到（说明原因，顺延）**。
   没走到目标页面就写「未走到」，不许写「应该没问题」。
6. **登记**：更新三处——(a) manifest 里该补丁的验证状态没有独立字段，写进当次的
   更新记录/PR 描述；(b) runbook `fix-lifecycle.md` §7 表格对应行；(c) 当次汇报里
   逐条点名每个补丁的状态。**任何一个补丁没恢复且没退役，当次更新不算完成。**

## 3. 冲突 playbook（CONFLICT 时按漂移类型对号入座）

锚点是按「语义块」选的（节点定义、next 数组原文），已避开 `desc` 行——发布包会
剥离 desc、仓库源码保留 desc，两边锚点通用。但上游改版仍可能让锚点漂移：

### 3.1 格式漂移（缩进/键序/换行变了，语义没变）
- 表现：节点还在、字段还在，锚点字符串对不上。
- 处理：用 JSON 解析定位目标节点，按新版文件的实际格式重写该条 edit 的锚点
  （保持「最小语义块」原则：选能唯一命中目标的相邻多行），在 fork 提一个只改
  `patches/manifest.json` 的 commit，注明「锚点随上游格式更新，补丁语义不变」，
  然后重跑 --check/--apply。

### 3.2 节点改名
- 表现：锚点里的节点名在新版不存在，但有语义等价的新节点（看它的 focus 文案、
  在链路中的位置、相邻节点）。
- 处理：确认等价关系后，更新 manifest 里该补丁的 edits 与 applied_markers 到新名，
  commit 注明「节点 X 更名为 Y，依据：<证据>」。拿不准等价关系 → 按 3.4 停手。

### 3.3 字段/数值被上游改动（同一位置改成了别的值）
- 表现：如 Pass_EnterPass 自带了一个 timeout 但不是 90000；IsMenu 的 roi 变成了第三组数。
- 处理：先判断上游新值是否已满足该补丁的 intent（对照 manifest 的 intent 与
  retire_when）。满足 → 走退役（第 4 节）；不满足 → 这是**语义冲突**，不要直接覆盖：
  在对应 issue 里记录双方数值与你的判断，汇报用户裁决后再动。

### 3.4 节点被删 / 流程重构（找不到等价物）
- 表现：整条链路被重写，补丁的前提不复存在。
- 处理：**停手**。该补丁标记为 `status: "needs-redesign"`（manifest 里改，加注日期
  与新版证据），在 issue 里写明，汇报用户。日常任务靠每日「阶段四 · 效果核查与
  补做」兜底（见每日 cron 正文），短期可运行，但汇报里必须点名缺失的补丁，
  不许当无事发生。

### 3.5 锚点多义（命中次数多于预期）
- 表现：--check 报 CONFLICT 且原因为命中 N 次 ≠ 预期次数。
- 处理：逐个列出命中位置，确认哪些是目标节点。若目标节点集合与预期一致只是
  计数口径变了（如同名 next 数组多了一处同语义引用），收紧锚点（加相邻行扩大
  语义块）或调整 count 并在 commit 里写清每个命中点的归属——参考
  quickhunt-locked-stage-fail 的 DoubleCk 锚点：它合法命中 3 个节点
  （DoubleCk1/DoubleCk2/RiceRecheck_DoubleCk，都是「点快速狩猎按钮前」的同语义检查点），
  manifest 里 count 就写 3。多出的命中若语义不同 → 按 3.2/3.4 处理，不要顺手一起打。

### 3.6 写后 JSON 校验失败
- applier 会自动拒绝写入并报错（它在写盘前已做校验）。出现时说明锚点替换破坏了
  结构：回滚到自动备份，回到 3.1 重新取锚点，不要手工修 JSON 凑合法。

## 4. 退役流程（上游原生修复时）

1. 证据：指出新版里覆盖 intent 的原生实现（节点/字段/数值），并按该补丁的
   `verify` 方法实机验证原生行为达标。
2. manifest 里把该补丁 `status` 改为 `retired`，在 intent 末尾追加
   「（YYYY-MM-DD 退役：<证据一句话>）」。不要删条目——退役记录是后来人判断
   「为什么不需要打」的依据。
3. 已部署目录里若还残留该补丁改动，不用特意回滚（新版目录替换时自然消失）；
   若是原地升级残留旧改动，按新版文件为准覆盖回去。
4. runbook §7 表格同步标退役。

## 5. 每条补丁的专属注意事项

- **pass-enter-wait**：90 秒是按通行证页实测加载（15 秒+）留足余量定的。
  不要改小；若上游给了一个较小的值（如 20000）而实测仍会假绿，按 3.3 走语义冲突，
  不要默默接受。EnterPass 的 on_error 链（Pass_Back → Global_Null_Exception →
  Global_Null_Panic）是「真进不去时显性失败」的出口，不要动它。
- **quickhunt-locked-stage-fail**：Panic 节点的 roi 与 stock 的
  `QuickHunt_QuickBattleButton` 共用（按钮文本区 [1029,632,89,33]，1280×720 参考坐标）。
  上游若调整了按钮位置/文案（如「快速狩猎」改名），两个节点要同步看。若游戏把
  按钮文案从「难度挑战」改掉，本补丁会静默失效（OCR 永远不命中）——抽验时
  必须实际造一次未解锁状态看它是否触发，不能只看 --check 的 APPLIED。
  它的 timeout 2000 是「不拖慢正常流程」的上限，不要调大。
- **event-battle-ismenu-roi**：这条至今未证成未证伪。抽验时若正式运行没经过挑战关
  详情页，如实记「未走到」，不要因为 --check 是 APPLIED 就写「正常」。
- **global-victory-return**：节点里的 roi/target 是 **1280×720 参考坐标**
  （roi [800,620,170,65]、target [880,655]）。v1 曾误写成 1920×1080 设备坐标而完全
  不触发——重打或改锚点时看到这组数字不要「纠正」成设备坐标。

## 6. 新增补丁的规矩（以后每加一条都照此办）

1. 先开 issue 写调查（现象、证据链、根因），补丁后提 PR 并 link issue；
   merge + 实机验证后才 close issue（全局 GitHub 纪律）。
2. 改动最小单点：一个补丁只解决一个已定因的问题；外科式文本编辑，不用
   json.dump 整文件重写（格式噪音会让 review 和锚点双双失效）。
3. 同时登记 manifest：id、intent（为什么打）、files、edits（锚点选最小唯一语义块，
   避开 desc 行）、applied_markers（怎样算已应用）、verify（怎样实机验证）、
   retire_when（什么条件退役）。六件缺一不许合并。
4. 自测 applier：在纯净树（git show 上游对应版本的文件）上跑通
   --check（PENDING）→ --apply（成功）→ --check（APPLIED）→ 再 --apply（无写入，幂等），
   四步全过才算登记完成。
5. 部署与验证按 fix-lifecycle.md 走；部署后必须重启 MFAAvalonia。
6. 同步 runbook `fix-lifecycle.md` §7 表格新增一行。

## 7. 红线

- 不许静默丢补丁：更新完发现某条补丁没了又不处理，是本指南的第一大忌。
- 不许在不理解 intent 时改锚点硬打：锚点对得上但语义变了，比打不上更危险。
- 不许删自动备份（`.bak-*`），它们是回滚源。
- 拿不准就停手汇报，把 --check 的原始输出贴出来——三态报告就是为此设计的。
